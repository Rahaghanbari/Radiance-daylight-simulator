# شبیه‌ساز محلی روشنایی

## چراغ‌های IES

در بخش «چراغ‌ها»، فایل `.ies` را بارگذاری کنید و موقعیت X، Y و ارتفاع Z چراغ را وارد کنید. بارگذاری، روش «شبیه‌سازی چراغ‌ها با Radiance / IES» را فعال می‌کند. ابعاد از فایل گرفته می‌شود؛ زاویهٔ صفر به سمت پایین است و چرخش‌ها به ترتیب X، Y و Z اعمال می‌شوند. برای چند چراغ مشابه، «کپی چراغ برای محل دیگر» را بزنید و موقعیت جدید بدهید.

نور روز، مجموع نور چراغ‌های فعال، و نور ترکیبی در هر سنسور فعال جدا محاسبه می‌شوند. در نتایج، انتخاب نقشه و نمودارهای نور طبیعی/مصنوعی/مجموع در دسترس است. حالت اندازه‌گیری لوکس سنسورها همچنان قابل انتخاب است؛ در آن حالت مدل IES استفاده نمی‌شود. روش انتخابی هنگام ذخیره و بارگذاری پروژه حفظ می‌شود.

پشتیبانی IES فعلی محدود به Type C، `TILT=NONE` و سطح تابندهٔ مستطیلی/جعبه‌ای است. فایل‌های اصلی در `runtime/uploads` نگهداری می‌شوند؛ فایل JSON پروژه شامل شناسهٔ آن‌هاست، نه محتوای IES. هنگام انتقال به دستگاه دیگر فایل IES را نیز منتقل یا مجدداً بارگذاری کنید. برای سهم مستقل یک چراغ، فقط همان چراغ را روشن و اجرا کنید.

## اجرای موازی زمان‌ها با ۸ ورکر

نسخه جدید، timestepهای مستقل شبیه‌سازی و نقشه‌های گزارش را با یک استخر
۸ ورکری اجرا می‌کند؛ اگر کمتر از ۸ زمان باقی مانده باشد فقط همان تعداد
هم‌زمان پردازش می‌شود. حالت‌های نور روز، چراغ و مجموع در داخل هر timestep
به‌ترتیب اجرا می‌شوند. پارامترهای کیفیت Radiance تغییر نکرده‌اند.

هر timestep پوشه جداگانه‌ای زیر `runtime/runs/<id>/timesteps/` دارد؛ فایل آسمان،
octree، RGB، فایل موقت و لاگ فرمان‌ها بین ورکرها مشترک نیستند. پیشرفت بر اساس
تعداد زمان‌های تکمیل‌شده است و خروجی نهایی به ترتیب زمانی ذخیره می‌شود.
در صورت خطا یا توقف، کارهای باقی‌مانده لغو و فرایندهای متعلق به همان اجرا
جمع‌آوری می‌شوند. مهلت هر فراخوانی rtrace در نسخه موازی ۳۶۰۰ ثانیه است.

برای فعال‌شدن تغییر، **پس از پایان اجرای فعلی** Backend را به روش معمول
دوباره اجرا کنید. فرایندی که از قبل در حال اجراست از کد بارگذاری‌شده قبلی
استفاده می‌کند و این تغییر تعداد ورکرهای آن را عوض نمی‌کند. فایل مستقل
`runtime/run_week_window_zones.py` مربوط به اجرای جاری تغییر داده نشده است.
عدد ۸ تعداد ورکرهای محاسبه زمان‌هاست؛ گزینه `uvicorn --workers 8` را اضافه نکنید.

## گزارش ساعتی تصویری

پس از پایان شبیه‌سازی، در «نتایج و مقایسه» دکمهٔ **تهیه گزارش** را بزنید.
قالب پیش‌فرض گزارش شامل نمودار مقایسه تمام سنسورها، پلان دارای پنجره‌ها و
پارتیشن‌ها با هیت‌مپ نور روز، جدول ساعتی تفکیک نور روز/چراغ/نور کل، و اطلس
نقشه‌های ساعتی است. خروجی‌های HTML تعاملی، PDF افقی و Excel در دسترس‌اند.

نمودار تمام نمونه‌های اصلی را نگه می‌دارد. جدول و نقشه، اولین نمونه موجود
در هر ساعت محلی را با تاریخ و زمان دقیق نشان می‌دهند؛ میانگین ساعتی یا
درون‌یابی زمانی انجام نمی‌شود. مقیاس رنگ بین ساعت‌ها ثابت است.
اگر اجرای اصلی شبکه داشته باشد همان نتایج استفاده می‌شود؛ در غیر این صورت
شبکه نور روز با فاصلهٔ پیش‌فرض ۰٫۵ متر و ارتفاع اولین سنسور فعال محاسبه می‌شود.
برای پروژه‌های بزرگ، فاصله شبکه افزایش می‌یابد و مقدار واقعی در گزارش درج می‌شود.
سهم اندازه‌گیری‌شده چراغ‌ها فقط در نقاط سنسور معتبر است و به نقشه نور روز تعمیم داده نمی‌شود.

تهیه اولیه نقشه‌ها ممکن است چند دقیقه طول بکشد؛ پیشرفت و دکمه توقف در برنامه
نمایش داده می‌شوند. توقف گزارش، نتایج شبیه‌سازی اصلی را تغییر نمی‌دهد.
گزارش‌ها در `runtime/runs/<job-id>/report/` ذخیره و برای دریافت بعدی استفاده
می‌شوند. بارگذاری اندازه‌گیری جدید، گزارش قبلی را نیازمند بازسازی می‌کند؛
داده شبکه قبلاً محاسبه‌شده دوباره استفاده می‌شود.

PDF با Node.js، بستهٔ موجود `@playwright/test` و Microsoft Edge نصب‌شده ساخته
می‌شود (`npm.cmd ci` وابستگی Node را نصب می‌کند). برای مرورگر دیگرِ پشتیبانی‌شده
می‌توان `REPORT_BROWSER_CHANNEL` را تنظیم کرد. اگر مرورگر در دسترس نباشد،
HTML و Excel همچنان آماده می‌شوند و «چاپ / ذخیره PDF» در گزارش HTML قابل استفاده است.
تغییرات Backend پس از راه‌اندازی مجدد آن فعال می‌شوند.

API گزارش: `POST /api/jobs/{id}/report` برای تهیه، `GET` همان مسیر برای وضعیت،
`POST /api/jobs/{id}/report/cancel` برای توقف و `GET /api/jobs/{id}/report/{html|pdf|xlsx}`
برای دریافت فایل. شناسه اجراهای تکمیل‌شده از فایل‌های ذخیره‌شده قابل بازیابی است.

## فرم ساده‌شده

نام پروژه فقط عنوان گزارش است. شناسه‌های پنجره، پارتیشن، پرده، سنسور و چراغ در فرم به‌صورت خودکار ساخته می‌شوند؛ شناسهٔ پنجره برای اتصال پرده به آن استفاده می‌شود.

در فرم، بازتاب دیوار و قسمت کدر پارتیشن ۰٫۵، کف و زمین بیرون ۰٫۲ و سقف ۰٫۸ ثابت است؛ بازتاب آینه‌ای و زبری این سطوح صفر است. این مقادیر همراه ورودی‌های اجرا ذخیره می‌شوند. API همچنان ورودی‌های صریح مصالح و شبکه را برای سازگاری پشتیبانی می‌کند.

پارتیشن می‌تواند شیشهٔ اختیاری با ارتفاع و عبور نور مرئی مستقل داشته باشد. ارتفاع پارتیشن مربوط به قسمت کدر است؛ شیشه از بالای آن شروع می‌شود و تمام طول پارتیشن را می‌پوشاند. شیشه یک صفحهٔ نازک با ضریب شکست ۱٫۵۲ است. مجموع ارتفاع قسمت کدر و شیشه نباید از سقف بیشتر شود.

فرم پرده فقط پارچهٔ تخت را ارائه می‌کند و ابعاد تیغه از فرم حذف شده‌اند. سنسورها با موقعیت X، Y و ارتفاع Z جداگانه وارد می‌شوند و شبکهٔ خودکار در فرم غیرفعال است. پشتیبانی قبلی کرکره و شبکه در API حفظ شده است.

این پروژه از یک workspace خالی ساخته شده است. Backend با Python/FastAPI و Honeybee، Frontend با React/TypeScript/Vite/Three.js است. محاسبه روشنایی فقط با Radiance انجام می‌شود. برنامه با فرم خالی شروع می‌شود؛ داده فیزیکی یا نتیجه نمایشی از پیش بارگذاری نمی‌شود.

## اجرای پروژه در VS Code / Windows

ترمینال را در ریشه همین workspace باز کنید. محیط مجازی و وابستگی‌های این تحویل در همین مسیر نصب شده‌اند. نیازی به فعال‌سازی PowerShell یا تغییر ExecutionPolicy نیست.

ترمینال اول:

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

ترمینال دوم:

```powershell
npm.cmd run dev
```

مرورگر: <http://127.0.0.1:5173> — قرارداد تعاملی API: <http://127.0.0.1:8000/docs>.

در VS Code، `Terminal → Run Task` نیز وظایف Backend، Frontend، Build را اجرا می‌کند. برای توقف سرویس‌ها در ترمینال Ctrl+C بزنید. توقف شبیه‌سازی از دکمه داخل برنامه انجام می‌شود.

برای اجرای نسخه ساخته‌شده با یک سرویس:

```powershell
npm.cmd run build
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

سپس <http://127.0.0.1:8000> را باز کنید. اگر Backend هنگام build روشن بوده، آن را مجدداً اجرا کنید. برنامه صرفاً روی loopback اجرا می‌شود؛ نیازی به حساب، دیتابیس یا سرویس ابری ندارد.

## نصب مجدد در همین workspace

Python 3.14.4 و Node.js 24.18.0 در این محیط استفاده شدند. Python با دستور `py` در دسترس است؛ `python` سراسری در این سیستم میان‌بر Microsoft Store است.

```powershell
New-Item -ItemType Directory -Force runtime/tmp | Out-Null
$env:TEMP = Join-Path (Get-Location) 'runtime/tmp'
$env:TMP = $env:TEMP
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install --cache-dir .cache/pip -r requirements-lock.txt
npm.cmd ci --cache .cache/npm
```

`requirements-lock.txt` نسخه‌های دقیق نصب‌شده را نگه می‌دارد. `requirements.txt` محدوده نسخه‌های مجاز است. برای کار عادی از فایل lock استفاده کنید. کش npm و pip و فایل‌های موقت را مانند دستور بالا داخل پروژه نگه دارید.

### Honeybee و Radiance

`honeybee-core` و `honeybee-radiance` با requirements نصب می‌شوند. Radiance اجرایی وابستگی جداگانه است. در این دستگاه نسخه `5.4.4ee32974b1` از قبل در PATH قابل اجرا بود و نصب سراسری آن تغییر داده نشد.

برای نصب جدید، بسته Windows را از [منبع رسمی Radiance](https://www.radiance-online.org/download-install) بگیرید، داخل workspace مثلاً `tools/Radiance` استخراج کنید و PATH/RAYPATH همان ترمینال را تنظیم کنید:

```powershell
$env:PATH = "$(Get-Location)\tools\Radiance\bin;" + $env:PATH
$env:RAYPATH = ".;$(Get-Location)\tools\Radiance\lib"
rtrace -version
Get-Command oconv,rtrace,ies2rad,gendaylit,xform,rcalc
.\.venv\Scripts\python.exe -c "from backend.engine import dependencies; print(dependencies())"
```

ساختار پوشه بسته دریافت‌شده باید با PATH بالا منطبق باشد. برنامه فایل‌های کتابخانه استاندارد Radiance را از مسیر `lib` کنار `bin` پیدا می‌کند. در صورت نبود ابزار یا شکست اجرای واقعی، شبیه‌سازی خطا می‌دهد؛ جایگزینی برای موتور وجود ندارد. `oconv` و `ies2rad` گزینه `-version` ندارند؛ نسخه مجموعه با `rtrace -version` ثبت می‌شود.

## مراحل استفاده

1. موقعیت، timezone از نوع IANA، بازه تاریخ و ساعت، گام دقیقه و بازتاب زمین بیرون را وارد کنید. تاریخ/ساعت شروع و پایان برابر یعنی یک لحظه. بازه ساعت در هر روز تکرار می‌شود.
2. ابعاد اتاق و مشخصات مستقل دیوار، کف و سقف را وارد کنید. ضرایب نوری باید داده معتبر کاربر باشند؛ هیچ مقداری حدس زده نمی‌شود.
3. پنجره، شیشه، پارتیشن، پرده تخت یا کرکره را در صورت نیاز اضافه کنید.
4. سنسورهای واقعی/مجازی و بردار عمود سطح دریافت را تعیین کنید. برای نقشه متراکم، grid را فعال کنید؛ هر نقطه آن واقعاً در Radiance محاسبه می‌شود. نقاط داخل پارتیشن با مختصات در گزارش حذف‌شده‌ها ثبت می‌شوند.
5. چراغ را با فتومتری IES یا توزیع لامبرتین ایده‌آل تعریف کنید. برای IES ابتدا فایل را بارگذاری و شناسه و ابعاد اعلام‌شده را وارد کنید.
6. برای تمام timestampها داده DNI/DHI/GHI/دما/آسمان وارد کنید یا API ساختاریافته را دریافت کنید. داده دریافت‌شده در فرم قابل بررسی است و با دریافت API شبیه‌سازی خودکار شروع نمی‌شود.
7. «اعتبارسنجی مدل» را بزنید و خطاها را اصلاح کنید، سپس اجرا کنید. وضعیت، زمان جاری، پیشرفت و توقف در UI نمایش داده می‌شود.
8. نتایج، slider زمان، انتخاب سنسور، سه نمودار، نقشه نقاط و Excel را مشاهده کنید. ویرایش ورودی پس از اجرا، نتیجه قبلی را تغییر نمی‌دهد و UI تفاوت نسخه ورودی را اعلام می‌کند.
9. CSV یا XLSX اندازه‌گیری را بارگذاری کنید. جدول مقایسه، نمودار زمانی، پراکندگی و نقشه اختلاف نمایش داده می‌شوند؛ ردیف‌های مشکل‌دار حذف پنهانی نمی‌شوند.

## قرارداد مختصات و فیزیک

- تمام هندسه‌ها برحسب متر هستند. مبدأ گوشه کف است؛ اتاق در `[0,length] × [0,width] × [0,height]` قرار دارد. Z رو به بالا، X طول و Y عرض است.
- نام دیوارها مربوط به محور مدل است: south یعنی Y=0، north یعنی Y=width، west یعنی X=0، east یعنی X=length. شمال جغرافیایی با زاویه ساعت‌گرد از +Y به +X مشخص می‌شود.
- موقعیت پنجره روی north/south از X=0 و روی east/west از Y=0 اندازه گرفته می‌شود. غیرفعال‌بودن پنجره یعنی دیوار کدر در آن محل.
- بازتاب سطوح سهم پخشیده مطلق است، specularity سهم آینه‌ای مطلق؛ مجموع حداکثر یک است. تبدیل به plastic با Honeybee انجام می‌شود. رنگ نوری خنثی RGB است.
- شیشه، صفحه نازک شفاف خنثی با ضریب شکست **1.52** است. VT به کمک Honeybee به transmissivity تبدیل می‌شود؛ مقادیر ناممکن توسط موتور رد می‌شوند. شیشه رنگی/چندلایه و BSDF دلخواه در این نسخه نیست.
- پرده تخت، ورق بدون ضخامت با عبور و بازتاب پخشیده است. جذب برابر سهم باقی‌مانده انرژی است. پرده حول مرکز پنجره قرار می‌گیرد و بالای آن هم‌تراز بالای پنجره است.
- کرکره، مجموعه تیغه‌های افقی کدر بدون ضخامت است. عمق، فاصله و زاویه تیغه ورودی‌اند. زاویه صفر یعنی تیغه افقی. نور از فاصله هندسی تیغه‌ها عبور می‌کند؛ transmittance تیغه صفر است. پرده باز کاملاً جمع شده و از هندسه حذف می‌شود.
- چراغ لامبرتین، یک سطح تابنده مستطیلی ایده‌آل است؛ بُعد Z باید صفر باشد. شار نوری به radiance سطح از تعریف دقیق Lambertian تبدیل می‌شود، نه به Lux تخمینی. جهت اولیه −Z و ترتیب دوران X سپس Y سپس Z است.
- IES فقط با `ies2rad` تبدیل می‌شود؛ در این نسخه فایل خودبسنده `TILT=NONE` و Type C با گشودگی مستطیلی/جعبه‌ای پشتیبانی می‌شود. ابعاد و توزیع از فایل می‌آیند؛ مقیاس‌گذاری حدسی یا تغییر ابعاد فتومتری انجام نمی‌شود. رنگ منبع خنثی است. فایل دارای ارجاع TILT خارجی یا MGF پذیرفته نمی‌شود.
- در همه حالت‌ها هندسه سطح تابنده حفظ می‌شود؛ در daylight-only و برای چراغ خاموش، گسیل آن صفر است. سطح Radiance light بازتاب ندارد. بدنه غیرتابنده چراغ به‌دلیل نبود مشخصات نوری مدل نمی‌شود.
- سنسور «واقعی» نیز در همان نقطه و جهت با Radiance شبیه‌سازی می‌شود تا نتیجه با اندازه‌گیری تطبیق داده شود؛ اندازه‌گیری خودش ورودی مستقل است و موجب اصلاح شبیه‌سازی نمی‌شود.

## زمان و هواشناسی

زمان UI براساس IANA timezone انتخابی است. timestamp داده دستی باید offset داشته باشد، مثلاً قالب `YYYY-MM-DDTHH:mm:ss+03:30`. تطبیق بر اساس لحظه واقعی انجام می‌شود؛ offsetهای متفاوت ولی معادل پذیرفته می‌شوند. زمان‌های محلی تکراری یا ناموجود DST در برنامه زمان‌بندی رد می‌شوند.

در API هواشناسی، timestamp بدون offset طبق timezone صریح همان منبع تفسیر می‌شود؛ موارد مبهم/ناموجود رد می‌شوند. پاسخ باید آرایه رکورد JSON یا CSV با header باشد. `records_field` مسیر آرایه داخل JSON است؛ نگاشت فیلدها صریح است. داده ستونی، HTML و scraping حدسی پشتیبانی نمی‌شوند. هیچ تبدیل واحد ضمنی وجود ندارد: DNI/DHI/GHI برحسب W/m² و دما برحسب °C.

API key فقط در متغیر محیطی Backend قرار می‌گیرد. نام متغیر و نام header را در UI بدهید؛ مقدار کلید را در فرم، کد یا URL نگذارید. پاسخ خطای اتصال، کلید یا URL حاوی پارامتر را نمایش نمی‌دهد. داده هواشناسی ذخیره می‌شود ولی پیکربندی دسترسی/API key وارد گزارش نمی‌شود.

`gendaylit -W DNI DHI -O 0` آسمان را می‌سازد. longitude شرقی و offset UTC با قرارداد علامت Radiance تبدیل می‌شوند. **GHI، دما، وضعیت آسمان و elevation در این مسیر محاسباتی دخالت ندارند** و فقط گزارش می‌شوند. DNI=DHI=0 آسمان بدون منبع می‌سازد؛ نتیجه همچنان از اجرای Radiance می‌آید.

## مسیر محاسبات و کیفیت

Honeybee هندسه بسته اتاق، apertures، مصالح، سایه‌ها و sensor grid را می‌سازد و صحت هندسه را بررسی می‌کند. سپس برای هر timestamp سه octree جدا با `oconv` و سه محاسبه مستقل `rtrace -I+` اجرا می‌شود. حالت مجموع جمع‌زدن frontend نیست.

پارامترهای ثابت و آشکار در `backend/engine.py`:

```text
-ab 5 -ad 4096 -as 1024 -ar 256 -aa 0.1 -dt 0 -dc 1 -dj 0 -lw 0.00001
```

خروجی RGB irradiance فقط با ابزار خود Radiance، یعنی `rcalc` و تبدیل فوتوپیک `179*(0.265*R+0.670*G+0.065*B)` به Lux تبدیل می‌شود. این تبدیل واحدِ خروجی موتور است، نه روش جایگزین شبیه‌سازی. بازتاب‌های چندگانه در Radiance محاسبه می‌شوند. نمونه‌برداری عددی ممکن است مجموع اجرای مستقل را اندکی متفاوت از جمع دو اجرای دیگر کند.

فایل HBJSON، ورودی Radiance، نقاط حسگر، octreeها، خروجی RGB خام، فرمان‌ها، هشدارها و نتایج در `runtime/runs/<run-id>` باقی می‌مانند. نسخه موتور، پارامترها و زمان اجرای UTC در metadata و Excel ثبت می‌شود. هیچ فرمان shell از ورودی کاربر ساخته نمی‌شود. فرایند در حال اجرا هنگام توقف kill و جمع‌آوری می‌شود؛ فرمان جاری timeout ده‌دقیقه‌ای دارد. نتایج ناقص به‌عنوان اجرای موفق ارائه نمی‌شوند.

## اندازه‌گیری و Excel

فایل اندازه‌گیری باید ستون‌های `timestamp,sensor_id,measured_lux` داشته باشد. timestamp دارای offset الزامی است (در Excel به‌صورت متن). Lux باید نامنفی و متناهی باشد. سنسور ناشناخته، زمان نامنطبق، شناسه/زمان تکراری و داده غیرمجاز با شماره ردیف گزارش می‌شوند. فقط ردیف‌های منطبق مقایسه می‌شوند. اختلاف = شبیه‌سازی مجموع منهای اندازه‌گیری؛ درصد = اختلاف تقسیم بر اندازه‌گیری ×۱۰۰. در اندازه‌گیری صفر، درصد تعریف‌نشده است و با — نمایش داده می‌شود.

Excel شامل Project Inputs، Weather Data، Virtual Sensor Results، Real Location Simulation و Simulation Metadata است. پس از بارگذاری اندازه‌گیری، Measured Comparison و Import Errors هم اضافه می‌شوند. رشته‌های ورودی به‌صورت متن نوشته می‌شوند تا به فرمول Excel تبدیل نشوند.

## محدودیت‌های صریح

- این پیاده‌سازی اتاق مستطیلی، مصالح خنثی، پرده تخت پخشیده و کرکره افقی را پشتیبانی می‌کند؛ مدل CAD دلخواه، شیشه پیچیده، توزیع نامشخص و هندسه بدنه چراغ ورودی این نسخه نیستند.
- فقط نقاط محاسبه‌شده رنگ دارند؛ نقشه بین نقاط Lux جدید نمی‌سازد. تصویر سه‌بعدی، نمایش هندسه است و خروجی رندر روشنایی نیست. نقشه XY، مختصات ارتفاع هر نقطه را در tooltip نشان می‌دهد.
- برنامه یک شبیه‌سازی همزمان، حداکثر ۲۰۰۰ زمان، حدود ۲۵۰۰ نقطه grid، ۳۰۰۰ حسگر محاسباتی و ۲۰۰۰۰۰ جفت زمان/حسگر می‌پذیرد. آپلود/API حداکثر ۸ MB و workbook بازشده حداکثر ۳۲ MB است.
- فایل‌های نتایج روی دیسک نگه داشته می‌شوند؛ رجیستری UI اجراها پس از restart Backend پاک می‌شود. بازیابی پروژه/اجرای قبلی از UI، دیتابیس و حساب کاربری اضافه نشده‌اند.
- API هواشناسی به فرمت مشخص و واحد صحیح نیاز دارد؛ هیچ ارائه‌دهنده یا داده آنلاین پیش‌فرضی انتخاب نشده است.
- تست واقعی موتور و سازگاری اجزای نور انجام می‌شود؛ این تست‌ها جای اعتبارسنجی آزمایشگاهی، مطالعه همگرایی یا تضمین دقت همه هندسه‌ها را نمی‌گیرند. هیچ ML، کالیبراسیون خودکار یا ضریب اصلاحی وجود ندارد.
